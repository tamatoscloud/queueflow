# Contributing / Development Standards

## Lints

`analysis_options.yaml` at the repo root is the single source of truth; every package/app `include`s it. It extends `flutter_lints` with:

- `strict-casts`, `strict-inference`, `strict-raw-types` (analyzer language modes).
- `directives_ordering` + `prefer_relative_imports` + `avoid_relative_lib_imports` for **import ordering**: `dart:` imports, then `package:` imports, then relative imports, alphabetized within each group; intra-package imports stay relative, cross-package imports are necessarily `package:` imports.
- Correctness/consistency rules: `unawaited_futures`, `cancel_subscriptions`, `close_sinks`, `use_key_in_widget_constructors`, `prefer_const_constructors`, `require_trailing_commas`, etc. — see the file for the full list.

Run `melos run analyze` before opening a PR; CI runs it with `--fatal-infos`, so warnings fail the build, not just errors.

## Formatting

`melos run format` (check) / `melos run format:fix` (apply). CI runs the check variant and fails on any diff.

## Code generation

Anything using `@freezed`, `@JsonSerializable`, or `@riverpod` must have its generated output committed... actually — generated files (`*.g.dart`, `*.freezed.dart`) are **gitignored** (see root `.gitignore`) and regenerated by `melos run gen` in CI before analysis/tests run. Never hand-edit a generated file; edit the source and regenerate.

## Dependency direction

See `docs/ARCHITECTURE.md` for the full graph. In review, reject any PR that:
- Adds a dependency from a lower-layer package (e.g. `queueflow_core`) to a higher one (e.g. `queueflow_services`) — that's a cycle.
- Adds `package:flutter` to `queueflow_core`, `queueflow_models`, `queueflow_network`, or `queueflow_utils` — they're pure Dart by design.
- Has one app-level `features/<a>` importing from another `features/<b>` directly — cross-feature communication goes through `packages/shared` or the app's own `shared/`.

## Dependency Injection

All cross-cutting services/config go through Riverpod providers with **no default implementation** where a missing override should be a loud failure (`appConfigProvider`, `dioProvider`, `flavorProvider`). When adding a new cross-cutting provider, ask: "should this fail if unoverridden, or is a sensible default fine?" — `appLoggerProvider` is the latter (defaults to `ConsoleAppLogger`), the others are the former.

## No duplicated code

Before adding a widget/util/model, check whether it already exists in `packages/ui`, `packages/widgets`, `packages/utils`, or `packages/models`. If you're about to copy-paste something from `customer_app` into `business_app` (or vice versa), it almost certainly belongs in a shared package instead.

## Commit hygiene

- One logical change per PR.
- If you touch `pubspec.yaml` in any package, run `melos bootstrap` and commit the result (no lockfiles are committed — see `.gitignore` — but verify the workspace still resolves).
- Update the relevant `docs/*.md` in the same PR if you change an architectural convention (dependency direction, environment variables, folder layout).
